# 设计研究与原型隔离

用于新界面、新功能、新模块和视觉改版。目标是先理解业务，再独立设计出符合产品规范的 UI。

## 搜索前先分清输入

| 输入 | 可以提取 | 不能默认作为 |
| --- | --- | --- |
| 线框图、业务原型、流程截图 | 内容、任务、状态、操作和业务约束 | 配色、字体、尺寸、留白、控件外观和视觉排版依据 |
| 指定正式设计稿、现有真实界面 | 对应范围的规范、控件、布局和品牌一致性 | 未授权整体改版的理由 |
| 外部优秀 UI 参考 | 对应模块的层级、布局、密度、控件呈现等设计启发 | 可直接整幅照搬的成品 |
| 品牌与真实产品资产 | 标识、配色、字体、照片、插图等获准素材 | 业务交互的推断依据 |

同一 Figma 文件可同时含原型和正式 UI，必须按页面/区域识别。不能把“用户给的 Figma 文件”整体视为 UI 参考。用户已经说明某图是原型，无须再询问。

先把原型转为简短的功能说明、真实文案、状态清单和约束；在视觉制作阶段使用这些文字，避免原型外观继续影响方案。保留必需的信息架构和业务顺序，不为了体现“独立设计”擅自改变业务。

## 参考来源白名单与质量门槛

**只从下列精选设计/UI 平台筛选视觉参考，按任务类型使用。** 平台知名不等于每件作品都合格；必须进一步检查具体作品。搜索引擎只是查找入口，不能把随机排在前面的网页当作优质参考。

| 来源 | 适用范围与筛选要求 |
| --- | --- |
| [Awwwards](https://www.awwwards.com/) | 品牌官网、营销页、创意网页；优先核实 SOTD / SOTM / SOTY 等获奖作品。普通投稿、提名或推广位不自动算获奖或优质。 |
| [Mobbin](https://mobbin.com/) | 移动端与 Web 产品 UI、具体控件及完整流程；筛选与任务相同的成熟产品画面，实际检查细节和可用性。 |
| [Godly](https://godly.website/) | 精选网页的视觉、排版、模块和动效方向；查看完整案例，不能凭缩略图把创意表现套到业务系统。 |
| [Land-book](https://land-book.com/) | 官网、落地页、电商等网页的排版与模块；筛选真正匹配本轮平台和用途的案例。 |
| [Refero](https://refero.design/) | 产品界面、网页与具体 UI 模式；优先完整上下文和实际产品案例，不以单个漂亮碎片代替业务设计。 |
| [Behance UI/UX](https://www.behance.net/galleries/ui-ux) | 编辑精选的完整 UI/UX 项目，或有可核验成熟案例的优秀设计团队原作；不采用任意普通投稿。 |
| [Dribbble](https://dribbble.com/) | 具体 UI、控件和视觉细节；筛选优秀设计师/团队的高质量作品，优先有完整案例支撑的原作；单张概念稿可借鉴局部视觉，但不能冒充成熟产品流程。不凭点赞或广告位认定为顶尖。 |
| [Pinterest](https://www.pinterest.com/) | 可作为正式参考入口，筛选优质 UI、网页排版和视觉方向的具体 Pin；实际打开查看清晰原图与来源链接，优先追溯到设计师/团队原作，记录 Pin 与可核验原作来源。排除模糊拼图、无关配图和无法识别内容的转载，不把收藏量当作质量证明。 |
| [站酷](https://www.zcool.com.cn/) | 站酷推荐/精选的完整 UI 项目，或优秀团队原作；明确推荐依据，不能把普通上传作品都当高质量。 |

- Behance、Pinterest、Dribbble 都是可直接检索和筛选作品的正式来源，不得因它们含用户上传内容而整站排除；质量门槛针对具体作品。Pinterest 优先查看 Pin 指向的原作；无法核实作者或精选身份时如实说明，不编造归属。相同原作在多个平台转载只计为一项参考。
- 品牌官网、工作室官网或产品实站可通过以上入选案例追溯并核对，记录发现来源及原作链接，不能借此任意扩大来源范围。用户指定的正式规范、参考和品牌材料仍按其要求采用。
- Apple、Material 等官方设计规范可用于平台规则与可用性核对，但阅读规范本身不能代替本轮实际视觉案例研究。
- **不采用**随机行业网站、搜索结果首屏任意图片、普通博客、教程截图、模板售卖页、素材站、来源不明的转载合集、模糊且来源不明的转载拼图或未经核实的 AI 生成图库作为视觉参考。它们最多帮助追溯原作，最终仍须找到白名单中的合格案例或其可追溯原作。
- 白名单网站打不开、付费内容不可见或找不到合格案例时，换白名单内的适用来源；不要绕过访问限制，也不要降级为随机网站。仍不足时说明缺口，请用户指定可用的专业来源或参考，不自行宣称陌生网站是顶尖平台。
- 不能把“顶尖”只理解成视觉炫酷。每项最终入选参考必须满足：平台/任务匹配、信息层级清楚、排版与留白精细、控件系统一致、实际可用、可查看且来源可追溯。成熟产品界面也应通过这些检查。
- 若使用“获奖”“编辑精选”“官方案例”等身份，必须有可核验页面依据；没有依据时不得编造，只能按实际确认的身份与设计质量判断是否合格。

每项对用户展示的参考补充一句“入选依据”：来自哪个精选来源/获奖类别/可核验团队，以及与本轮任务相关的具体质量。之后再说明具体借鉴点。不要只罗列知名平台名称，而不打开其中的具体作品。

## 必须完成的外部研究

1. 按平台、页面/控件用途、用户任务、内容密度和品牌方向使用中英文关键词搜索。同类后台表格应搜索后台/数据管理参考，不用营销首页代替；移动端弹窗也不应套用桌面海报。
2. 至少检索两个白名单内且与任务相关的来源，按上述质量门槛筛选三项优秀参考。采用站内搜索或带站点限制的搜索，优先精选/获奖栏目和成熟产品真实画面。不必遍历所有平台；宁可说明合格参考不足，也不使用普通作品或随机网站凑数。
3. 实际打开并查看参考图片、页面或截图。只有搜索标题、摘要、文字描述，或打不开的缩略图，不算完成。确认作品确实包含需要借鉴的模块。
4. 每项记录：具体作品/产品名称、准确来源链接、已查看的图片/页面、可核验的入选依据、具体适用范围、可借鉴的设计特点。构图、字号层级、列表密度、色彩比例、间距、控件状态等应具体到能指导设计。
5. 在首张样张、视觉素材或直接制作正式 Figma 前，向用户展示链接、实际图片/截图和简短借鉴说明，提出统一视觉方向。无需让用户先批准搜索结果；完成后默认制作样张等待确认，用户已明确要求直接生成 Figma 时则直接制作。

模块参考允许只覆盖特定范围，不冒充整页范本。不能用三张原型、三个重复转载或三张无关网站截图凑足数量。不得编造链接、看图结果和作品细节，也不能先制作后补研究。

### 搜索失败与例外

- 某来源受阻时换白名单内其他适用来源或该精选案例可追溯的原作页面，不反复请求同一失效地址，不降级到随机网页。
- 工具无法展示图片时，尝试可用的截图/图像输出；向用户说明哪些图实际看过、哪些无法展示。无法实际看图的来源不能记为有效参考。
- 无法完成有效搜索/看图时，说明具体限制，询问用户提供可用视觉参考或明确允许跳过。继续整理业务与原规范，但不悄悄沿用原型外观生成新 UI。
- 用户明确“不要搜索”时遵从，用其批准的参考或品牌规则开展独立视觉设计，并记录免搜索依据。历史关键词限制不能覆盖本 Skill 对新设计主动研究的要求。
- 已确认样张落稿、同一方向迭代，以及字号/描边/布局等局部修复，沿用现有研究，不重启选风格。若要建立新的视觉方向或此前没有实际研究，则补齐对应研究。
- “直接做 Figma”可以跳过样张确认：先完成联网研究、看图与方向说明，再直接制作原生 Figma。它不免去独立 UI 设计，也不授权将原型作为视觉参考；该授权仅覆盖本轮对应范围。

## 把研究转成 UI，而不是拼贴

形成一个简短设计方案：
- 业务：当前任务、主要信息和操作优先级。
- 正式规范：必须复用的字体、颜色、控件、尺寸及来源。
- 新视觉：对缺失部分确定布局、层级、密度、间距、材质与状态呈现。
- 参考分工：每个借鉴点来自哪项参考、用于哪个模块；不混合互相矛盾的视觉体系。

现有产品优先延续正式设计系统，参考为新增部分补齐设计；全新产品据参考形成一致体系。独立设计不等于创造全新交互，也不意味着弃用已有正式组件。

## 制作输入的硬性边界

- 原型以语义文字进入制作，不作为视觉参考图、风格图、待美化底图或图生图输入。
- 不因为所有图片都在聊天里，就把全部图片一并传入生图；明确选择真正的 UI 参考/正式设计截图。工具仅能引用最近若干张图且无法排除原型时，不使用这种笼统引用，改用可精确选择的参考路径或根据已查看参考编写设计说明。
- 工具支持且参考可获取时，优先输入实际 UI 参考，并标明“只借鉴布局/密度/控件表现”等适用范围。仅能文字表达时如实说明，不声称工具已收到参考图片。
- 正式现有界面作为上下文时，标明需要复用的规范与本轮设计区域；不把整页简单重绘作为新设计。
- 提示词/构建说明写出具体视觉决定、准确文案、平台尺寸、资产用途和需避免的问题。不能仅写“把这张原型变高级”。

## 交付前的判断

核对样张与原型：内容和业务关系应一致，视觉应有独立规范依据。没有既有正式规范支持时，若原型的粗糙卡片比例、文字排布、间距和控件外观被整体沿用，仅加色彩/投影/圆角，应返回重新设计。

核对样张与参考方向：借鉴点是否真正落实，是否受品牌与现有规范约束。不要为了证明改动大而增加无用装饰。合格标准是完整、清晰、一致、可维护的 UI，而不是与原型越不同越好。
